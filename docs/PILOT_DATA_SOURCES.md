# Preparing the shipment evaluator for company data

Primary-source research checked on 17 November 2026. This note supports the preparation work authorized after Bahaa's advisor meeting. The pilot's actual CRM, transport system, agent platform, permissions and data remain unconfirmed. Vendor examples below explain integration behavior that we should be able to handle. They do not identify CMA CGM's internal technology stack.

## What we can prepare before getting access

We can prepare a documented export contract, reusable field mappings, timestamp and identifier validation, duplicate and conflict handling, an evidence-coverage assessment and repeatable imports. A company sample is still needed to establish whether its records support each calculation. A successful import can establish format compatibility while leaving factual verification, human effort or attribution unavailable.

The first practical route is an authorized batch of exported records, followed by a read-only API adapter when the source owner has confirmed the relevant system, API version and permissions. The same normalized evidence contract can serve both routes. This is our engineering recommendation. The public documentation establishes that these products offer export and query mechanisms, with materially different access and pagination rules.

## A company-facing sample request

We would request a small authorized sample that follows several original enquiries and their continuations through all relevant systems. The sample should contain the following where the company actually records them.

| Record family | Fields and context to ask for | Calculation it can support |
| --- | --- | --- |
| Customer request and delivered reply | Stable pseudonymous customer/account, original request and contact IDs, receipt and send timestamps, channel, language, actual visible text, request reference and delivery state | First-answer timing, interpretation and answer checks |
| Authoritative shipment evidence | Booking/B/L/container references, milestone and leg/location, event ID, created/published time, event time, classifier, source-system revision or retraction | Reconstructing tracking evidence available when the answer was sent |
| Agent activity | Correlated agent release and model ID, tool-call IDs, inputs, returned result/status, timestamps, technical failures and retries, billable usage, handoff and send evidence | Verifying actions, separating exposure from assignment, model cost and latency |
| Service history | Case ID, original request link, owner changes, escalation and follow-up events, close/reopen history, closure reason and customer confirmation where present | Validity of the eventual outcome and follow-up compliance |
| Human work | Work-item and actor IDs, links to cases or contacts, recorded active duration, interval boundaries, measurement semantics and edits | Documented effort and its coverage |
| Allocation and operations | Which eligible requests went to each policy, assignment time/method, actual exposure, deployment changes and workload/channel/region definitions | Comparison eligibility and credible deployment or upgrade attribution |
| Finance | Applicable labour and vendor rates with effective periods, invoice line IDs, currency, fixed charges, credits and refunds, setup/maintenance scope | Reconciled resource costs and cost completeness |
| Downstream logistics | Dispatch/appointment, release/availability, gate-in/out, warehouse acceptance and final invoice/credit linked to the payer and container | Investigating whether a timely correct response changed a feasible action and financial consequence |

The source owner should also provide the schema, field meanings, export method, requested and delivered date ranges, time zone, row counts, retention and sampling limits, known exclusions, and contact responsible for corrections. Stable pseudonyms must be applied consistently across all extracts. Ask the company to remove unrelated content before transfer while retaining the minimum evidence required for the agreed checks. These are proposed data requirements, subject to feasibility and authorization.

## Validation and import behavior to exercise before a pilot

1. Check the file and schema contract, read the original bytes once, record hashes and row positions, and produce a report of accepted, rejected and incomplete inputs. Preserve original values alongside mapped identifiers and units.
2. Check identity separately from similarity. A booking with several containers needs container-level evidence for a container-specific answer. Preserve orphan records and ambiguous contact links in the quality report.
3. Test explicit UTC offsets, local time mappings, daylight-saving ambiguity, late publication, reordered events and revisions. Rebuild evidence at each checkpoint before judging the answer.
4. Distinguish an exact repeated record from a conflicting version. Define source precedence with the company and version the rule. Preserve conflicting evidence until the source owner resolves it.
5. Treat unrecognized closure codes, missing action histories, sampled traces and unreadable text as gaps affecting specific capabilities. An optional finance file should not prevent inspection of otherwise usable service records.
6. Reconcile totals across raw imports, mapped output, discarded duplicates and excluded populations. Commit an import or cursor after its artifacts are complete. Repeating the same input should reproduce the same numerical analysis.
7. Exercise missing assignments, human rescues, open and reopened cases, mixed currencies, billing periods crossing study dates, tariff changes, duplicates and invalid timestamps. Compare against manually reviewed examples before applying the mappings at scale.

These checks are proposed engineering behavior derived from the documented source limitations and the project's evidence principles. They do not establish that the current code supports every source-specific feature.

## What a reusable adapter cannot settle

The current benchmark assumes a narrow set of tool names, structured reply claims and reviewed English request patterns. Its sent-run linkage also expects a run end time matching a response time and matching delivered text. A real platform can separate generation, sending and acknowledgement. We need actual correlation IDs and delivery evidence to adapt that contract. Renaming columns cannot supply evidence that the company never logged.

A static export of the latest tracking ETA cannot prove what was visible months earlier. Likewise, present ownership cannot establish past authorization, active call duration cannot establish all back-office effort, and a self-reported successful tool call needs authoritative case or dispatch confirmation where that outcome is material.

The pilot still requires independently reviewed fields, workflow rules, transcript interpretation and sample outcomes. A company may provide sufficient evidence for service checks while leaving cost completeness or causal attribution unavailable. Live API credentials, network setup, retention policies and production deployment will be scoped after the company selects the authorized source route.
